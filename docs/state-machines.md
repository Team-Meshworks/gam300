# Spatia state machines

Living inventory for the signed-in Spatia editor, workspace, server and published visitor. It follows dev at `1560743` and the fixes in this stack. Source links identify the transition owners. The evidence tables distinguish failed-before/passed-after regressions from unconfirmed reports. A lost response does not identify whether a write committed. [SCRUM-180](https://meshworkss.atlassian.net/browse/SCRUM-180).

## Cross-cutting invariants

- The authored document is authoritative. Rendering, selection, camera and drag previews are session state. Validate project data before loading or saving, and preserve IDs through history and persistence. See [project validation](../apps/web/shared/project/project-validation.ts), [document store](../apps/web/editor/document-store.ts), and [architecture](architecture.md).
- A save cannot claim success without its matching receipt, overwrite newer work silently, or replace a conflict. An uncertain retry keeps the same identity and payload. The server rechecks authorization. See [autosave](../apps/web/editor/persistence/server-autosave.ts), [save progress](../apps/web/editor/persistence/server-save-progress.ts), and [save policy](../apps/server/Spatia.Server/Projects/ProjectSavePolicy.cs).
- Submissions, decisions and publications bind to project revisions. A later edit can make a submission or approval stale; the server enforces access and revision guards independently of UI controls. See [submissions](../apps/server/Spatia.Server/Reviews/ReviewSubmissionEndpoints.cs), [decisions](../apps/server/Spatia.Server/Reviews/ReviewDecisions.cs), and [publication coordinator](../apps/server/Spatia.Server/Publications/PublicationCoordinator.cs).
- Cleanup cancels or retires asynchronous work. Shared model resources stay alive until borrowers release their leases. See [model cache](../apps/web/shared/asset-runtime/ModelCache.ts) and [visitor canvas](../apps/web/visitor/ExhibitionCanvas.tsx).

## Document, undo history and authoring

| Starting state | Event and preconditions | Next state | Observable effect |
| --- | --- | --- | --- |
| No document | Open or create a valid project | Current document, initial history | Install one project and a valid active scene. Reopening discards transient selections and the old clipboard. |
| Current document | Command produces a changed, valid snapshot | Current advances, past grows, future clears | One undo reverses the edit. Bound the retained history. |
| Current document | Rejected, throwing or unchanged command | Same history | No phantom undo step or partial authored update. |
| Past or future available | Undo or redo applies the corresponding entry | Move one entry to the other stack | Restore document, IDs and active scene together. |
| Move idle | Begin valid drag | Preview against captured transform | Renderer moves a preview outside the saved document. |
| Dragging | Move, then release with valid changed geometry and matching before-value | Committed or canceled | Commit the transform and affected descendants in one command. Invalid geometry, stale transform, mode change or cancel restores the preview. |
| Selection or pending text | Scene/object disappears or document is replaced | Reconciled selection or canceled placement | Filter object IDs against the current scene and tie pending text to scene and load generation. |
| Display editor open | Request a display fit, then cancel, replace the target or close before it completes | Closed or new editor | Only the still-mounted owner may commit the captured selection. |
| Scene, named view or hierarchy selected | Create, rename, reorder, duplicate, remove or restore a valid entity | Updated document or validation error | Preserve references and undo removed dependants with the same edit. A saved viewpoint changes the camera through an explicit selection. |

The document store owns authored data and history. The renderer, display editor and selection controls own transient previews. Restoring recovery validates complete snapshots and discards invalid history independently of a usable document. ## Browser checkpoints, project files and departure

| Starting state | Event and preconditions | Next state | Observable effect |
| --- | --- | --- | --- |
| Account/project open | Commit an edit | Checkpoint queued | Capture document, matching undo history, server baseline and pending retry separately. |
| Checkpoint queued or writing | IndexedDB transaction commits at its expected revision | Checkpoint confirmed | Advance the storage revision only after commit. Writes from one owner are ordered. |
| Checkpoint writing | Stale revision, storage failure or final write fails | Conflict or retained in memory | Keep current edits and protect the newer stored copy. Reattachment by the original account compares validated document bytes. |
| Confirmed recovery | Final cleanup for the matching revision | Cleared marker | Remove payload and retain the revision. A new write increments it, excluding an old tab even after cleanup. |
| Opening | Account/project key contains a valid checkpoint, empty marker or older backup | Recovery choice, server version or export | Offer to reopen stored edits, including a captured retry. A marker has no document to restore. Leave legacy unscoped keys alone. |
| Editing | Export chooses a file handle | Exclusive writer open | Compare captured baseline after acquiring the writer. Close confirms the write; mismatch or failure aborts the acquired stream. |
| Editing or leaving | File picker canceled or download fallback | Editing | A download attempt cannot confirm bytes at the chosen destination. |
| Importing | Validate file and current project, flush, recheck account and record a create attempt | Created, rejected or uncertain | Create a separate project. A lost response preserves the marker and directs the user to All Projects. |
| Dirty or blocked | Leave, reopen or sign out | Preservation choice | Cancel keeps edits. Save, local recovery or export must preserve the captured bytes before departure. Native unload also checks dirty status. |
| Preserving | Matching operation finishes while the project changes, or an operation fails | Still editing | Retain work and offer retry or export. Confirming the selected destination ends the session before navigation. |
| Saved | Leave or explicitly save | Departed or confirmed | Leave directly when clean. A confirmed manual save plays the save cue. An unsaved departure opens the prompt and plays the warning cue. |

The signed-in session owns departure and in-memory recovery. An IndexedDB commit, an exclusive file close and a matching server receipt acknowledge different destinations. ## Server autosave and replay

| Starting state | Event and preconditions | Next state | Observable effect |
| --- | --- | --- | --- |
| Saved | An authored document changes | Unsaved | Advance local edit sequence and schedule a save. A view-only notification schedules nothing. |
| Unsaved | Valid flush with known revision | Saving | Capture one document, revision and mutation ID. Commit the retry checkpoint before sending. |
| Saving | Later edit or overlapping flush | Saving with newer dirty work | The active request stays immutable. Additional flushes share the active operation. |
| Saving | Matching project, mutation and next-revision receipt | Saved, unsaved or checkpoint failed | Advance the confirmed baseline, persist the acknowledgement and schedule any later edits. |
| Saving | Network failure, missing or wrong receipt | Failed with pending request | Preserve original bytes, revision and ID. An explicit retry resends them even if a later draft contains an unfinished link. |
| Saving | Definite 422 with code `invalid_document` | Invalid, or unsaved if a newer correction exists | Retire the uncommitted attempt. A correction uses a fresh ID at the same revision. |
| Saving | Revision conflict or other definite rejection | Conflict or rejected | Stop network writes until owner resolution. Blank links, subsequent edits and checkpoints cannot erase that block. |
| Failed, no unacknowledged request | Retry a confirmed save whose local backup failed | Saved or unsaved | Retry the browser checkpoint without sending another project write. |
| Local-only invalid draft | Correct a link during the checkpoint | Unsaved → saving when valid | Recheck current document on completion and schedule even if the debounce already fired. |
| Recovery pending | Open valid baseline and authorized project | Resumed or blocked | Replay the original request separately from latest local edits. The server recognizes actor, ID, digest and original revision before admitting a new mutation. |
| Any live session | Dispose or replace account/project | Retired | Stop timers and network activity and queue a final local snapshot. Late acknowledgements cannot update the new editor. |

The autosave owner separates work in flight from current edits. The server serializes new writes on the project row and checks current authority before replaying a durable receipt, including after later revisions. [Autosave](../apps/web/editor/persistence/server-autosave.ts), [progress](../apps/web/editor/persistence/server-save-progress.ts), [recovery validation](../apps/web/editor/persistence/server-save-recovery.ts), [HTTP result classification](../apps/web/editor/persistence/server-draft-write.ts), [save service](../apps/server/Spatia.Server/Projects/ProjectSaveService.cs), [transactional writer](../apps/server/Spatia.Server/Projects/ProjectSaveWriter.cs), [save policy](../apps/server/Spatia.Server/Projects/ProjectSavePolicy.cs), [SCRUM-66](https://meshworkss.atlassian.net/browse/SCRUM-66), [SCRUM-179](https://meshworkss.atlassian.net/browse/SCRUM-179).

## Runtime playback, public delivery and resources

| Starting state | Event and preconditions | Next state | Observable effect |
| --- | --- | --- | --- |
| Opening publication | Manifest, document, capability set and assets pass checks | Ready at first scene | Render immutable published edition. A rejected load shows error/retry. |
| Ready | Focus or periodic access check while visible | Checking with current exhibition | Only the current check may withdraw the exhibition. A superseded denial or network failure has no visible effect. |
| Checking | Current check denies access or fails | Unavailable | Retire the load attempt, release its canvas and restore the generic title. A held initial response cannot publish a retired edition. Retry initializes a new visit. |
| Scene active | Start or elapsed trigger matches | Actions running | Execute in author order. Elapsed rules fire once per reset. Accepted cross-scene navigation ends processing in the departing scene. |
| Automatic navigation chain | Target revisits a scene in the current chain | Still in current scene | Reject the transition without marking playback as departing. Succeeding actions may still run. |
| Visitor acts deliberately | Click a target or scene/view control, or deliberately walk/look | New deliberate interaction | Begin a fresh chain. Dispatch point click rules before the default target. A handled navigation happens once. |
| Playing, awaiting media or permission blocked | Ready, explicit user gesture, pause, hide, replace or dispose | Playing, deferred, stopped or disposed | Start only the live element, honor permission and visibility, and discard results from replaced playback attempts. |
| Model absent or loading | Acquire by model identity/version and placement | Shared pending load or lease | Separate waiters from delivered leases. Abort orphaned loads and dispose results arriving after retirement. |
| Loaded | Invalidate, release last lease, expire or exceed idle cap | Retired, idle or evicted | Remove invalidated lookup immediately. Dispose resources after the last borrower releases. |
| Viewport loading | Renderer initializes, download fails, authority changes or graphics unsupported | Ready, error, download-error, authentication-required or unsupported | Show the corresponding canvas, retry, sign-in or fallback. Replacing the attempt retires old work. [Viewport statuses](../apps/web/editor/graphics/scene.ts). |
| Viewport model queue | Request or retry failed load | Queued, loading, ready or failed | Deduplicate per attempt and bound active loads. Explicit viewport retry creates a new queue; unmount cancels/releases resources. |

| --- | --- | --- | --- |
| Submission adapter editing | Student completes then submits | Completed → submitted | The host must confirm the same submission and revision and the state expected for the action. |
| Adapter submitted | Teacher saves feedback or approves | Submitted or approved | An unexpected result stays unconfirmed. |

## Persistence and session ownership

The [save progress tracker](../apps/web/editor/persistence/server-save-progress.ts) owns each pending mutation, its original request bytes and revision, and the last confirmed document. [Autosave](../apps/web/editor/persistence/server-autosave.ts) schedules checkpoints and sends the captured request. The [server project session](../apps/web/editor/persistence/server-project-session.ts) captures the matching undo history before queuing a checkpoint. Only a committed transaction advances the account/project storage revision, including a final checkpoint after disposal.

[History validation](../apps/web/editor/recovery-history.ts) compares validated document contents across checkpoints, including after an undo upgrades a version-1 scene. [Recovery storage](../apps/web/editor/persistence/recovery-session.ts) validates account-scoped records, retains cleared revisions and reads the existing version-2 envelope. The [database opener](../apps/web/editor/persistence/draft-db.ts) owns the store name and schema. The signed-in editor and facilitator preview use the [asset reader](../apps/web/editor/persistence/server-assets.ts) directly. Standalone editing and local-file migration were retired on dev.

Four [save progress cases](../apps/web/editor/persistence/server-save-progress.test.ts) cover restored attempts with and without newer edits, definite rejection, and a mismatched server revision. A [held IndexedDB write](../apps/web/editor/persistence/local-drafts.test.ts) exercises two edits, undo during a pending departure, sequential storage revisions, and undo after reopening the second checkpoint.

## Coverage and limits

The tables cover the product states represented by the linked owners. Visual hover/focus values, demo fixtures, deployment infrastructure and browser/library internals are outside the product inventory. The historical regressions above are distinct from guarantees about every possible asynchronous ordering.

- Organization and asset creation have no server-side idempotency receipt. A separately initiated request, another browser profile or a deliberate new upload after catalogue review may create another record. The organization marker is shared within an origin/account. The asset browser test asserts issued writes and UI recovery against a controlled lost acknowledgement. The intake and deletion tests exercise PostgreSQL.
- Browser file exclusivity was verified on OPFS. An external OS writer is outside that evidence. Disputing a recovery checkpoint still requires a separate confirmed save, retained backup or export before departure.
