# API write recovery

The API uses cookie sessions. A 401 problem includes `WWW-Authenticate: SpatiaSession realm="Spatia", login_uri="/api/v1/auth/login"`. This private challenge points to the cookie-session login. A protected read after session expiry returns 401. Obtain `requestToken` from `GET /api/v1/auth/csrf` and send it as `X-CSRF-TOKEN` with the antiforgery cookie on unsafe requests, including login and recovery POSTs. The session cookie is `__Host-Spatia.Application` and the antiforgery cookie is `__Host-Spatia.Antiforgery`. Development and Production append their environment name, such as `.Production`. Reauthenticate and reacquire the token when needed. Recovery rechecks current authorization.

A lost response does not establish whether a write committed. Some protected writes return an empty, no-store 204 with `X-Spatia-Write-Outcome: committed` when authority changes after commit. This confirms the write while withholding its representation. Reauthenticate as the original actor and use the relevant receipt or authoritative read below. A plain 204 has no such outcome header. If the response itself was lost, preserve the original operation identity and payload.

## Project and class creation

`POST /api/v1/projects`, `POST /api/v1/projects/{id}/duplicate`, and `POST /api/v1/classes` accept a non-empty UUID in JSON `operationId` or the `Idempotency-Key` header. The header is one raw 36-character hyphenated UUID, with no whitespace, braces or comma list. Hexadecimal case is ignored. If both are supplied, they must identify the same UUID. An empty, malformed or conflicting identifier returns 400 `invalid_creation_operation_id`; malformed JSON binding also returns 400. Header and body forms identify the same operation for replay. A new keyed creation returns 201 and a `Location` for `/api/v1/projects/{id}` or `/api/v1/classes/{id}`. An authorized exact replay by the same actor returns the original representation with 200 and the same location. Reusing an ID with a different kind or request returns 409 `operation_conflict`. Duplicate identity also includes the source project ID. Preserve the original request when retrying. Current access is required, including access to the duplicate source. Deletion or lost authority can prevent replay. Organization deletion removes the stored representation and retains the operation key as a tombstone.

Before a new creation, read `GET /api/v1/creation-operations/{purpose}`. Purposes are `project`, `class`, `duplicate`, `import`, and `assignment-source`. The no-store response is `{ operationId, state, receipt }`. An `unacknowledged` state identifies the newest outstanding operation for this actor and purpose. The receipt contains the original response object when current resource and source access permit disclosure. Otherwise it is null. A `ready` state has no outstanding receipt. Its operation ID is the latest generation, or null before any operation.

After inspecting an outstanding outcome, `POST /api/v1/creation-operations/{purpose}/{operationId}/acknowledge` with `{}` closes that actor's matching operation and returns no-store 204. It is idempotent for an existing matching receipt. An unknown operation returns 404 `creation_operation_not_found`. An old acknowledgement cannot close a newer operation. Read again, because an older outstanding receipt may then appear. Acknowledging records a decision and does not undo the created resource.

To start a new operation, send a fresh UUID `operationId` with `creationGuard: { purpose, previousOperationId }`, using the ready response's operation ID, including null for the initial generation. The server serializes by actor and purpose. A changed predecessor or outstanding receipt returns 409 `creation_state_changed`. Exact keyed retries can replay their original receipt even after the head advances. A client on another browser profile can discover outstanding server receipts after signing in as the same actor. The server retains metadata and a digest, not another authored document or image.

Deploy the receipt-aware server and migrations `20261114135210_AddCreationReceipts`, `20261114150108_AddCreationGenerations`, and `20261114170716_AddLegacyCreationBindings` before clients rely on this protocol. Stop and drain old hosts and unkeyed writers before enabling the release or header-only traffic. An old host could ignore the header and create without recording its key. Clients can prepare JSON body keys where supported. A newly generated key cannot identify an older unkeyed commit. The migrations refuse a downgrade that would discard populated receipt, generation or resolution history. Existing keyed v1 callers can continue without a guard. A key alone permits exact retry, while the generation guard prevents a fresh request from racing an unresolved operation.

## Resolving an unkeyed integration

An authenticated, valid unkeyed POST with no prior resolution returns 400 `creation_operation_id_required` and a `resolutionUrl`. The `Link` header also identifies that URL with `rel="related"`. It writes nothing. The operator can use the same account and original request body to make one explicit decision at that URL. The decision is bound to the actor, route and request. The digest uses the typed outer request fields. Preserve nested imported-document property and array order, and class manager array order, for retries. Titles do not deduplicate requests. The decision does not assert who created any pre-upgrade record.

1. Sign in as the integration's actor, obtain a current CSRF token and inspect `GET /api/v1/projects` or `GET /api/v1/classes`, including subsequent pages. Review archived projects separately with `?archived=true` when relevant. For an existing resource, choose its exact UUID after reviewing it with the people involved. Names are not proof. Duplicate resolution also requires current access to its original source.
2. To adopt an existing resource, send the unchanged original JSON body to `PUT <resolutionUrl>?useExisting=<selected-uuid>`. The selected project must be visible and owned or managed by the actor in the intended organization. It may be active or archived. A selected class must be in that organization and currently manageable by the actor. For a duplicate, the selected project must differ from the source, which must be nonarchived and currently editable. A successful response is 200 with current authorized metadata, including the project's revision and archive flag, and `X-Spatia-Creation-Resolution: existing`. This creates no historical receipt and does not unarchive the project.
3. To deliberately create a separate resource, first read `GET /api/v1/creation-operations/{purpose}` and resolve any unacknowledged operations. An unkeyed project request with a document uses `import`; a bare project request, including an old assignment-source create, uses `project`. Duplicate and class requests use `duplicate` and `class`. Once the head returns `ready`, use `createAfter=initial` if its operation ID is null, or `createAfter=<operationId>` for that observed ready head. Send the unchanged original body to `PUT <resolutionUrl>?createAfter=<value>`. A successful first response is 201 with `X-Spatia-Creation-Resolution: created`. Its receipt and resolution commit together. A replay returns 200.

For example, if an unmodified integration's `POST /api/v1/projects` with body `{"title":"Gallery"}` receives `/api/v1/projects/legacy-resolution` as `resolutionUrl`, an operator who has reviewed the selected ID can send the following request using the current authenticated cookie jar:

```http
PUT /api/v1/projects/legacy-resolution?useExisting=11111111-1111-4111-8111-111111111111
Content-Type: application/json
X-CSRF-TOKEN: <current requestToken>

{"title":"Gallery"}
```

To create separately from an initial ready head, use `?createAfter=initial` instead. Use the returned URL for the actual original route, including a duplicate source ID.

If the resolution reply is lost, repeat the same PUT with the same decision and original body as the same actor. If the operator no longer knows which decision was sent, the unchanged unkeyed POST also returns the stored result and its `existing` or `created` header. Once resolved, every identical unkeyed POST from that actor selects the same resource indefinitely, even after acknowledgement or later keyed work. A deliberate second identical creation needs a fresh modern keyed intent. A conflicting decision returns 409 `legacy_creation_resolution_conflict` and cannot rebind it. Changing from `createAfter` to `useExisting` conflicts even if the ID names the created resource. The PUT accepts exactly one decision and no operation key or guard. Malformed decisions return 400 `invalid_legacy_creation_resolution`. Another actor or changed request is a separate resolution. Deleted resources or lost authority can prevent resolution or replay. Denials and committed-but-withheld 204 responses do not disclose the resolution header. No browser-stored identifier or old cookie is needed beyond current authentication.

The generation migration leaves existing keyed receipts unacknowledged. Older project receipts cannot distinguish project, import and assignment-source purposes, so they enter the `project` scope. Their migration order follows UUID order and does not imply creation chronology. Old duplicate receipts without a recorded source are redacted on discovery. The original direct retry can still return the receipt after authorizing its source. The migration cannot reconstruct genuinely unkeyed historical creates. Older server binaries cannot write incomplete generation records after migration, so use a coordinated server rollout.

For pre-upgrade unkeyed work, preserve the existing resources and review the accessible lists with the people involved before starting a replacement. A matching name or timestamp cannot identify the original request or actor. Historical project grants and class manager memberships can change, and an administrator can create a class for other managers. A project's latest mutation actor identifies a later remembered save, not necessarily its creator. Assignment creator records identify an assignment action, not creation of its source project or class. See [project schema](../apps/server/Spatia.Server/Projects/Project.cs), [class schema](../apps/server/Spatia.Server/Classes/Classroom.cs), and [assignment schema](../apps/server/Spatia.Server/Classes/ClassAssignment.cs).

A retained historical operation ID can be used for exact recovery only when it identifies the original keyed request. The old assignment-source `attemptId` was a local marker and was not sent to the server. The old project-creation and import session marker was only a sentinel, with no ID or request payload. A saved response may contain a project ID that can be checked against current access. Supplying a fresh ID cannot prove or recover a create that the old server accepted without an ID. Keep the earlier resource and investigate it before choosing a separate creation.

The workspace can list accessible active and archived projects with their IDs so a person can review an exact existing record. Educators can explicitly select an active project they currently manage as an assignment source, including from a fresh profile. Selection rechecks access and revision and is preserved locally across reload. Archived or unmanageable projects cannot be selected as a source. Duplicate names remain separate choices. This is an explicit choice of a current resource, not proof that it resulted from an earlier request.

For an import retry, reselect the same file. In the browser, a successful project, copy, import or class creation leaves its receipt available across profiles. Review and accept the receipt in the workspace before starting a separate creation for the same purpose. A session recheck clears the previous review and requires a fresh choice. When choosing a recovered assignment source, the browser rechecks manage access and saves the selected source locally before acknowledging the server receipt. If local preservation fails or another source record has replaced the observed one, acknowledgement is not sent. A reload can restore the selected source and recheck it before assignment.

[Creation receipt tests](../apps/server/tests/CreationReceiptTests.cs) cover concurrent replay, actor and kind conflicts, and canonical locations.

## Bulk account imports

All routes below require the issuing administrator's current authority and CSRF for unsafe methods. Let `B` be `/api/v1/admin/organizations/{orgId}/bulk-imports`. `PUT B/{operationId}` accepts a JSON array of 1–200 accounts, at most 1 MiB. Every row requires `userName`, `initialPassword`, `role` and `orgId`. `displayName` is optional and falls back to the username. Names must be nonblank and at most 256 characters. Passwords must be 12–128 characters. Each role is `Creator` or `Educator`, and every non-empty `orgId` must match the route. The organization must be active. Existing usernames and duplicate normalized usernames in the same request are skipped. New usernames are subject to Identity validation and uniqueness.

For example, the body can be `[{"userName":"student1","initialPassword":"example-password","role":"Creator","orgId":"11111111-1111-4111-8111-111111111111","displayName":"Student One"}]`. A fresh successful PUT returns 201. An exact replay returns 200. Both return an object with `operationId`, `orgId`, `created`, `credentials`, `expiresAt`, and `acknowledged`. Each `created` entry has `userId`, `userName`, `displayName`, and `role`. Each available credential has `userId`, `userName`, and `password`. Reusing the ID with different input returns 409 `bulk_import_conflict`.

`GET B?limit=20&cursor={operationId}` lists the issuer's unacknowledged, unexpired receipts for an active organization. It returns `{ items, nextCursor }`. Each item contains `operationId`, `createdAt`, `expiresAt`, and `createdCount`. Results are ordered by operation UUID, with a default limit of 20 and maximum 50. Omit `cursor` for the first page.

`POST B/{operationId}/receipt` with `{}` returns the receipt object with 200. `POST B/{operationId}/acknowledge` with `{}` returns 204 and erases the protected credential handoff. `POST B/{operationId}/abandon` with `{}` returns 204 when it fences an absent or already abandoned operation. A committed operation returns 409 `bulk_import_committed` and should be recovered. A later submit against an abandoned ID returns 409 `bulk_import_abandoned`. Missing or inaccessible receipts return 404. Credentials are recoverable for up to 24 hours by the issuer while the account, organization, temporary password and security stamp remain eligible. The created-account list remains in the receipt after acknowledgement or expiry. See [bulk transitions](state-machines.md#workspace-write-lifecycles).

Legacy `POST /api/v1/admin/users/bulk` accepts the same array and returns the existing array of provisioned account records. It returns 201 when accounts were created and 200 for an empty result. When it creates accounts, `X-Spatia-Operation-Id` identifies the generated receipt and the issuer can discover it through `GET B`. A zero-created legacy request creates no discoverable receipt. A lost legacy response can be reconciled through the issuer's list. `POST /api/v1/admin/users` returns 201 with `Location: /api/v1/admin/users/{id}`. New organizations return 201 with their organization location, while an existing active name returns 200. [Account directory](account-directory.md) describes lifecycle rules.

## Drafts and publications

Draft saves use `PUT /api/v1/projects/{id}` with the original `clientMutationId`, expected revision and exact document representation. Retry those same bytes after uncertainty. An authorized matching receipt confirms the original revision even if a newer revision exists. A different payload or revision for an accepted ID conflicts. See the [draft save contract](../apps/server/README.md#draft-save-retry-contract). Publication creation retains its publication ID and original revision, audience and viewers for exact retry. Read the publication and its access state to reconcile moderation changes. A later denial does not prove the first request failed. See [publication transitions](state-machines.md#submission-review-and-publication).

Single-project and bulk publication moderation use the same transaction path. A bulk selection locks projects in a consistent order and commits all selected changes together. A rejected item rolls back the selection. Read the current moderation state after an uncertain response. See [moderation endpoint](../apps/server/Spatia.Server/Publications/ProjectPublicationModerationEndpoints.cs).

## Assets

Asset intake identifies a retry by the bytes' SHA-256, filename label without extension, kind and category. A matching retained candidate returns its existing record and consumes no additional quota, including when retired. New candidates count against `AssetIntake:MaxRetainedAssets`, which defaults to 1000 and accepts 1–100000, and `AssetIntake:MaxRetainedBytes`, which defaults to 1073741824 and must be positive. Standard .NET configuration uses environment variables such as `AssetIntake__MaxRetainedAssets`. Invalid configuration prevents startup. The individual upload cap remains 20 MiB. Full retained capacity returns 409 `asset_quota_exceeded`. Validation or storage unavailability returns 503 `asset_intake_unavailable`.

In `compose.server.yaml`, set `SPATIA_ASSET_MAX_RETAINED_ASSETS` and `SPATIA_ASSET_MAX_RETAINED_BYTES` to override those defaults. Retired and invalid candidates retain bytes and count against capacity. The administrator list and selectable catalogue are bounded at 100,000 entries independently of the configured intake quota. A historical catalogue above that bound is not truncated in storage, but its list snapshot is bounded. See [asset intake](../apps/server/Spatia.Server/Assets/AssetAdministrationService.cs) and [catalogue delivery](../apps/server/Spatia.Server/Assets/AssetDeliveryEndpoints.cs).

The administrator snapshot orders candidates newest first. The selectable catalogue orders IDs ascending. [Asset contract tests](../apps/server/tests/AssetContractTests.cs) cover configured limits and retained bytes.

The administrator catalogue list has a separate per-account fixed-window limit of 60 per minute. Account writes use 20 per minute. Both fall back to IP when no account is resolved. Asset intake and byte delivery each have separate global concurrency limits of two, in addition to the global limit. Rejected requests are not queued.

For removal, `PUT /api/v1/admin/assets/{assetId}/removals/{operationId}` accepts an empty JSON object. Exact replay returns the current asset record. Operation IDs are actor-scoped and cannot be reused for another asset. By default the response is 200. A client requesting `Prefer: spatia-created-status` gets 201 for a newly created removal receipt and 200 for replay, with `Preference-Applied: spatia-created-status`. A confirmed removal response includes `X-Spatia-Operation-Id`. `POST` to the same path plus `/reconcile` with `{}` returns `removed` or `notApplied`. The latter fences a delayed request with that identity. Keep the ID until reconciled.

The legacy availability remove action uses the asset ID as its operation ID. To reconcile it, use the same reconcile route with `{operationId}` equal to `{assetId}`. Historical removals predating receipts cannot always be attributed. Reconciliation can return 409 `asset_removal_history_unavailable` when the server cannot establish the outcome. A repeated legacy removal can return 409. Read and reconcile before starting another operation.

New operation bindings reserve asset IDs for their own legacy paths. Using another existing asset's ID returns 409 `asset_removal_conflict`. Existing actor-scoped receipts keep their original target even if the operation ID matches another asset. An applied receipt replays or reconciles as removed. A not-applied receipt retains its fence and reconciles as not applied. Cross-target use returns 409. The ID must be nonzero. Receipt history is retained with the actor and asset. See [removal endpoint](../apps/server/Spatia.Server/Assets/AssetRemovalEndpoints.cs) and [receipt tests](../apps/server/tests/AssetRemovalReceiptTests.cs).

## Deployment

The organization deletion browser uses `POST /api/v1/admin/organizations/{id}/deletion` with the exact-name confirmation in JSON. The versioned legacy `DELETE /api/v1/admin/organizations/{id}` remains supported with the same body. This is separate from removed unversioned `/api/...` routes. Proxies must forward either method and body unchanged. The browser does not fall back to DELETE after a lost POST response. Read organization state after reauthentication when the outcome is uncertain.

The [restricted-assets proxy check](../deploy/restricted-assets.check.mjs) exercises TLS to the host gateway and loopback HTTP to the inner gateway. It verifies the deletion methods and a legacy-resolution PUT, including the original body, decision query, cookie, CSRF token, actor, resolution header and location. This is a local deployment check. Repeat it against the intended deployment path.
