# SCRUM-12: library and runtime performance evidence

The user reported a transient FPS drop when starting to pull a library asset into the creator scene. This report records a bounded investigation and changes. The baseline is `fixes_UI_backend` at `7374128beff53e18ef4e778149e4dd817acc97eb`. The candidate includes uncommitted work. Acceptance on agreed devices and representative content remains open under [SCRUM-12](https://meshworkss.atlassian.net/browse/SCRUM-12) and its parent [SCRUM-52](https://meshworkss.atlassian.net/browse/SCRUM-52).

The creator now prepares a selected asset earlier and preserves a quick first placement. Background thumbnail generation removes a measured main-thread library-opening task and duplicate placement readback. A single desktop drag trial improved its worst fixed-window frame interval from 99.8 to 16.8 ms. The phone-sized CPU-emulated trial instead worsened from 83.4 to 116.7 ms while completing a placement the baseline lost. Physical mobile verification and the remaining first-use work are open. The separate visitor change reuses loaded assets and reduced repeated-scene CPU submission and resource counts in the measured fixture, with unchanged captured pixels and draw calls.

## Creator library

The creator baseline includes pre-existing uncommitted renderer preparation work. It is not the pinned player baseline. Source hashes were captured with the benchmark. In a general-library baseline, the first Sample crate placement succeeded. Opening the library also generated an offscreen snowglobe thumbnail. One synchronous `renderer.render` took approximately 594.5 ms, a long task reached 599 ms and the observed animation-frame interval reached 600.1 ms. This observation concerns opening the library. It does not establish the cause of a later drag stall. A main-thread precompiled candidate reduced the render to 223 ms, still substantial. In the final worker run the card image took 625.5 ms to become available, with zero main-thread thumbnail draws/readbacks and zero long tasks during that interval. Worst frame interval remained 83.4 ms. Worker and forced main-thread fallback PNGs differed in 631 of 409,600 channels, by at most 1/255. Results are in `apps/web/test-results/SCRUM-12/drag-start-worker-general-verified/result.json`.

For an explicitly selected bench with a supplied thumbnail, the candidate starts asynchronous model preparation on selection rather than waiting for Add. It does not prefetch on hover or indiscriminately. In the matched 500 ms dwell scenario, the last of eight uploads occurred approximately 354 ms after selection, before Add at 561 ms. The baseline began parsing 646 ms after selection, after Add at 543 ms. In a separate no-dwell bench probe, immediate native drag and touch placement each produced zero placed objects on the baseline. The final candidate's desktop first and second drags produced one and two rows, with the first row 309 ms after quick release. There were no frame intervals over 33 ms after the first-drag marker, compared with a 99.8 ms maximum on baseline. One 4× CPU-throttled, 390 × 844 DPR 2 phone-sized touch run succeeded but reached a 116.7 ms frame interval versus 83.4 ms baseline. Maximum texture initialization was 40.6 versus 55.7 ms. This observed frame regression or run-to-run variation gives no smoothness guarantee. Emulation is not a physical mobile device and spreading work cannot eliminate an individual upload stall. Two desktop UI audio requests were aborted. There were no page errors. Results are in `apps/web/test-results/SCRUM-12/drag-start-final/result.json`.

The 116.7 ms emulated interval overlapped successful object creation, whereas baseline lost that object. Its trace included a 111 ms input task and 28 ms render, with the peak texture call elsewhere. The gated regression passed cold mouse and touch placement, Escape, outside release, and a 503 response with no partial placement. In-viewport invalid geometry was not established by that test.

The lost first placement had an input-lifetime cause. While loading, the stage used `pointer-events: none`, so native drop reached the outer viewport while its handler required a ready model. Touch Add likewise waited for geometry before arming. The creator now captures the world hit during the gesture, validates bounds, room and parent once loading finishes, and discards stale or cancelled document, scene, selection or renderer requests. The two-slot model queue promotes the picked model and places authored requests ahead of outstanding optional work. See the [creator](../../apps/web/editor/App.tsx) and [model queue](../../apps/web/editor/graphics/model-load-queue.ts).

For the fixed 1,200 ms after the `before-first` marker, counting frame intervals ending in that window:

| Input environment | Samples, baseline → candidate | Average FPS | Frame interval p50 / p95 / p99 (ms) | Gaps over 50 ms |
| --- | --- | --- | --- | --- |
| Desktop mouse | 67 → 72 | 55.8 → 60.0 | 16.7 / 16.8 / 99.8 → 16.7 / 16.8 / 16.8 | 1 → 0 |
| Phone-sized 4× CPU emulation, touch | 49 → 52 | 40.8 → 43.3 | 16.7 / 50.0 / 83.4 → 16.7 / 66.6 / 116.7 | 2 → 3 |

These are single trials. The candidate performs placement in this window while the baseline loses the input, so the work differs.

The measured bench GLB is approximately 9.18 MB transferred, with 1,978 triangles and two materials, but four 2048² and four 512 × 1024 images. RGBA8 storage calculates to 72 MiB at base level or approximately 96 MiB with a full mip chain. Neither is measured resident GPU memory. The texture workload helps explain why low geometry alone does not rule out a first-upload hitch.

A separate short simulated-touch CPU profile sampled a 36 ms render in the commit task, with approximately 15.9 ms sampled in a React passive effect → scene update → Three.js `setProgram` → `getProgramInfoLog` stack. This dev/headless trace does not prove duplicate same-turn renders, and no batching change was inferred from it.

Ordinary generated thumbnails now use an OffscreenCanvas worker, with a `compileAsync` main-thread fallback and shared CPU cache retaining the original render settings. The special room-choice crop remains on the main thread. Worker startup and fallback availability, actual mobile GPUs, and the observed remaining frame gap still need field-device verification.

After the snowglobe card image was ready, an additional regression found placement still rendered and read back a duplicate thumbnail on the live editor canvas, taking 271 ms in that run. The creator now requests outstanding thumbnails through the same background generator and reuses generated picker images. Restored scene thumbnails retain their scene lighting and framing. A real placement regression then recorded zero live thumbnail draws/readbacks, and a saved project reload showed the snowglobe row image with zero live thumbnail draws/readbacks. Built Vite preview verified decoded picker and restored scene-tree images from the worker with no main-thread 320-pixel draws/readbacks, page errors or failed requests. The lazy worker adds an approximately 621 kB minified, 155 kB gzipped independent Three.js bundle and parses its own model in a separate context.

The editor's animation loop follows `requestAnimationFrame`. Its FPS display averages at least 500 ms. A brief long frame can therefore be followed by a near-60 display when later frames return near the approximately 16.7 ms interval on this host. This path does not set a hard 60 FPS value.

A real cache/viewport lifetime check prepared six preview-only assets and waited 31 seconds. Before the ownership fix zero of six leases were released and zero of ten geometries disposed. Afterward six leases were released and ten geometries disposed, and an evicted asset could be reloaded and previewed. Renderer geometry count fell from 11 to one. The room-preview, placement-collision, moving-room, nonstarter-room, empty-project-room, model-preparation, caching and furniture browser suites passed. The first nonstarter run exposed a gray ghost/placement mismatch. The cold-ready pointer reset was corrected and the rerun passed. Model-preparation, caching and full room-preview were rerun after the lifetime fix. These checks do not replace repeated physical-device testing.

The editor scene, current choice and placement ghost hold leases while needed. The shared model cache bounds idle entries to three, 30 seconds and an estimated 128 MiB of decoded data. Active assets are exempt. See the [editor scene](../../apps/web/editor/graphics/scene.ts), [model cache](../../apps/web/shared/asset-runtime/ModelCache.ts), [lifetime check](../../apps/web/tests/editor-model-lifetime.check.mjs) and [thumbnail reuse check](../../apps/web/tests/live-thumbnail-reuse.check.mjs).

## Visitor repeated-scene comparison

On the same local RTX 5060 host, a repeated-scene browser benchmark compared the pinned baseline with the candidate. Initial asset fetches and parses fell from 21 each to three each. Across seven mounts they fell from 99 fetches and parses to 18 fetches and three parses. Initial canvas captures were pixel-identical (zero differences among 800,000 pixels). Both submitted 418 calls and 330,904 triangles. Stationary renderer counts fell from 225 geometries and 26 textures to 41 and four. Three returns plateaued at 41 and four after the candidate's scene/camera reuse correction. An earlier candidate failed this plateau, rising from six to ten textures, and was corrected before this final run.

The player verifies authorization and SHA-256 once for each distinct catalogue descriptor on each visit, including warm visits, then reuses parsed templates and shared geometry, materials and textures while instances own their transforms and bones. A stable renderer, scene and camera avoid accumulating transmission targets. Frames without enabled gaze rules skip full-scene gaze raycasts, and hidden frames pause. The benchmark checks reuse and the resource plateau. See the [player](../../apps/web/shared/player/ExhibitionCanvas.tsx) and [benchmark](../../apps/web/tests/player-performance.measure.mjs).

The browser was headless Chrome 158.0.8127.37 on Windows, ANGLE/D3D11, 1000 × 800 at DPR 1, with a local intercepted publication API. The fixture has nine interconnected rooms and 12 models. Two seconds of warmup preceded each five-second sample. Walking and fast camera rotation were exercised. An illustrative extreme of 20 room changes per second was not tested. Results are single runs per version. FPS below is frame count divided by total sampled interval, not a low-percentile FPS.

| --- | --- | --- | --- | --- |
| Stationary | 16.7 / 16.8 / 17.0 → 16.7 / 16.8 / 16.9 | 60.00 → 60.00 | 2.9 / 4.2 / 5.5 → 1.4 / 2.8 / 3.0 | 2.24 / 3.57 / 4.53 → 3.46 / 4.98 / 5.57 |
| Walking and rotation | 16.7 / 16.9 / 17.2 → 16.7 / 16.8 / 17.0 | 59.83 → 60.02 | 0.5 / 3.6 / 4.0 → 0.5 / 1.7 / 2.0 | 2.89 / 5.34 / 6.22 → 2.97 / 4.07 / 4.96 |

CPU values time render submission, not total CPU work. GPU times use available nonblocking disjoint timer queries, not frame intervals.

In a separate 40-return soak on the same host, baseline versus candidate recorded 1,061 versus 203 fetches, 1,061 versus three parses, and 81 versus one renderer creations. Baseline produced 65 WebGL context-limit warnings. Candidate produced none and no errors. Same-view geometry/texture counts stayed 225/26 versus 41/4 over all returns. Natural-GC renderer-main tracing recorded 116 minor and 28 major events totaling 228.8 ms versus 20 and six totaling 38.7 ms. Automation and tracing affect the result. Forced-GC heap rose from 10.86 to 17.40 MB versus 9.00 to 10.75 MB, but the harness accumulated different amounts of frame data (1,440 versus 483 entries), so these values do not establish an application leak. Resident GPU bytes were not measured. Raw observations are in `apps/web/test-results/player-performance-sustained-baseline/` and `apps/web/test-results/player-performance-sustained-candidate/`.

Initial ready time was 1,836 ms versus 1,236 ms. Return-to-first-scene times were approximately 401 ms versus 100–169 ms. Scene-switch intervals over 50 ms fell from seven to one, and CPU render submission p95 from 55.3 to 3.5 ms. Stationary frame p99 was 17.0 versus 16.9 ms. GPU timing p95 was 3.57 versus 4.98 ms. This variation does not support a GPU improvement claim. Counts are fetch/parse and renderer resource counts, not individual GPU uploads. The hidden-state check simulated the handler rather than actual browser background throttling. Movement endpoints differed by approximately 2 cm. There were no browser warnings or errors.

The visitor, preview/visitor parity and player-walking browser suites passed, including rules, visibility, navigation, media, gaze, zone and wall/doorway behavior. The full unit suite passed 1,208 tests. Local benchmark artifacts are `apps/web/test-results/player-performance-baseline-final/` and `apps/web/test-results/player-performance-candidate-final/`. This is one desktop host, not a physical mobile-device result, and does not establish the Jira performance target.

Both production builds, TypeScript and the live architecture scan passed, with no forbidden edges or cycles. The clean full `node architecture.check.mjs` run passed 14 isolated probes and all 15 module-removal cases with active source hashes unchanged. The visitor build reported a 916 kB minified chunk warning. Native lint could not load under host Windows Application Control. Supplemental configured React hook checks passed on transpiled changed TSX. Real network latency and physical mobile devices were not tested.

Both active paths use Three.js r186 `WebGLRenderer`, antialiasing and a DPR ceiling of 2, with the same three-light rig and fog, default frustum culling, no `EffectComposer` and no enabled dynamic shadow-map pass. The snowglobe uses physical transmission. Original GLBs, images, mipmaps, DPR and scene detail were preserved. Cold mobile timing remains open. The player still submits 418 calls in the measured view. There is no authored room/portal graph for potentially visible sets, and batching independently editable, pickable or transparent meshes needs its own behavioral and performance evidence. The unchanged `untitled-v1.glb` is 93,690,356 bytes. A separate header audit found ten 4096² textures and 497,964 triangles before culling. No frame-time result for that asset was obtained.
